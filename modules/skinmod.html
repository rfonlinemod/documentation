Skin Mod (Skins, Glows & Particle Effects)

Server Client FX layer ships off Hot-reload

What it does — and why you would use it

Skin Mod is the live appearance editor for everything a player sees on a character, weapon or creature: the coloured glow that rides an upgraded weapon, a cloak’s aura, a helmet’s sparkle, a monster’s particle puff — and the actual particle emitters behind them (their colour, size, lifetime, speed, gravity and spawn count). Normally all of that is baked into the shipped .EFF / .spt / .r3e binaries and the compiled client, so changing one glow meant editing binary art files and re-shipping the whole client.

This feature lifts the whole thing into plain-language .lua files on the Server. You edit a value, save the file, and the running Zone server notices it within about a second, validates it, and pushes just that change to every player’s Client over the skin-mod message channel (system msg family 1, index 57). The change shows up in-game, live, with no restart and no rebuild. Set the value back (or delete the row) and save, and it reverts just as fast.

The game client is your preview windowBecause the change is pushed live, the intended workflow is: edit → save → look at your character in-game → tweak → save → when it looks right, copy the runtime file back to the source folder to commit it. You are authoring against the real renderer, not a guess.

READ FIRST: the three golden rules

Ninety percent of “my edit did nothing” reports come from breaking one of these three. Read them before touching anything.

  1. Edit Override, never Properties. Inside every particle row of SptIndex.lua there is a big Properties = { ... } block. That block is read-only reference data — the server never ships it, so changing a number there is a permanent silent no-op. The only thing that takes effect is a sibling Override = { ... } table you add yourself. (This is the single most common mistake.)
  2. Edit the RUNTIME copy, not the source tree. Hot-reload watches .Server\Zoneserver\RF_Bin\Modules\SkinMod\ only. The identically-named files under _server\WorldServer\Features\ini\SkinMod\ are the source of truth for committing — editing those has zero live effect until you deploy them.
  3. One glow → many indices; one index → many items. A weapon’s glow is not one particle: it fans out across several particle indices across its upgrade levels, and each index is shared by many other items. To recolour a specific item you override all the indices that item uses (see Finding your item’s indices) — overriding one may not touch the emitter you can actually see. Conversely, editing a shared index changes every item that uses it.
Colour is a tint over the sprite, not a paintA particle’s StartColor multiplies its texture. A white/gold spark tinted green goes olive, not lime. If a glow is a solid-coloured .EFF ribbon rather than a tinted particle, a particle Override will not reach it — that look is a SkinFX job (retarget the effect file, or edit its TextureFactor).
Setting only StartColor often looks like it “did nothing”An emitter’s birth colour is only the start of the story: its stock .spt carries life Keys colour tracks that interpolate every particle toward the original hue over its lifetime. So a StartColor-only Override flashes your colour for a frame and then snaps back to the shipped look — the glow still reads as its old colour. To recolour durably you must override the Keys too, setting Color on every keyframe (writing Keys replaces the whole track). See the worked green-aura example below.
Need the complete item → particle INDEX reference?Every shipped particle index, its .spt baseline values, and which item codes attach it are in the interactive SptIndex Particle Authoring Guide — search by item code or filter by equipment slot, then click an index to jump to its values.

The files

All live in .Server\Zoneserver\RF_Bin\Modules\SkinMod\. There are three kinds: the effect-override engine (three files you edit), and the per-slot skin record files (auto-generated reference the server uses to match item codes to meshes / glows).

FileEdit?What it is
SkinFX.luaauthor hereThe FX-override master switch and your workspace for retargeting one glow/aura to a different stock effect file, and for field edits on an effect (tint colour, scroll speed, attached particle id, material colour…). Ships Enable = false.
SkinPropRegistry.luaInfra (keep on)The property registry — every editable visual parameter, with the struct / offset / size / kind the client writes it to. Adding a new editable = adding one row here. The client refuses any row whose offset is outside a compiled allow-list, so a typo can never crash it.
SptIndex.luaauthor hereThe parsed inventory of every shipped particle / entity index (a real whitelist the server uses to reject bad edits), plus the live Override blocks for particle colour / size / speed / gravity / lifetime / keyframes. The Properties sub-blocks are read-only reference; you add a sibling Override.
WeaponSkin.lua, UpperSkin.lua, LowerSkin.lua, ShoeSkin.lua, GauntletSkin.lua, HelmetSkin.lua, CloakSkin.lua, ShieldSkin.lua, MauSkin.lua, LauncherSkin.lua, MonsterSkin.lua, AnimusSkin.luaGenerated (read to look up)One file per equipment slot: one record per item code with its mesh, its glow Effect.Glow entries and its Attached.Particle indices. You read these to discover which particle indices / effect files a given item uses. Editing an appearance goes through SkinFX.lua / SptIndex.lua, not these.

How to activate it

  1. Particle overrides — ready to use. SptIndex.lua runs with Enable = true already. You only add Override blocks to the indices you want to change (see below). No global switch to flip.
  2. FX overrides — flip the master switch. To retarget an effect or edit an effect field, open SkinFX.lua and change Enable = false to Enable = true, then add rows under Retargets / Fields.
  3. Save & watch. Saving the runtime file applies it live in about a second — a running Zone server hot-reloads it, no restart. Look at your character in-game.
  4. Commit when happy. Copy the edited runtime file back to _server\WorldServer\Features\ini\SkinMod\ so the change survives a fresh deploy.
  5. Revert any time. Delete the Override / row, or set SkinFX back to Enable = false, and save — that appearance returns to stock and clients get a reset push.
Do not delete these files, and expect an empty folder to break the bootLike every module, the SkinMod files are required when the Zone server starts — an empty Modules\SkinMod\ folder makes the server abort (“…could not be started”). To turn a piece off, use its Enable switch or delete individual rows — never remove the files. Client-side effects only appear on a game client rebuilt with Skin-Mod support; a stock client ignores the push and keeps its shipped look.

Changing a particle (colour, size, speed)

Find the index you want in SptIndex.lua (each is [INDEX] = { Spt = "...", Properties = { ... } }) and add an Override table as a sibling of Properties. Only the keys you list are overwritten; everything you leave out stays at its stock value.

Worked example — turning the axe’s aura green (the real override shipped in SptIndex.lua). The 55AXE glow is built from two of its particle indices: 670 is the big rising aura (.\Chef\55LV_WEAPON\55AXE\670p.spt, live_time 3) and 669 is the 60 small sparks. The first attempt set only StartColor — the aura flashed green then snapped back to its stock colour within a second, because 670 carries life Keys colour tracks that dominate the birth colour:

-- WRONG: StartColor alone is overridden by the emitter's stock Keys colour tracks
Override = { StartColor = { R = 0, G = 255, B = 0 } },   -- still looks yellow

The fix is to override the Keys as well, pinning Color green on every keyframe (and enlarging the subtle sparks so the change is unmistakable). This is the block now in the runtime SptIndex.lua:

-- 670 = the rising aura. StartColor + every Keys frame green => colour sticks for the whole life
[670] = {
    Spt = ".\\Chef\\55LV_WEAPON\\55AXE\\670p.spt",
    Override = {
        StartColor = { R = 0, G = 255, B = 0 },
        StartAlpha = 255,
        Keys = {
            { Time = 1, Alpha = 255, Scale = 8,  Color = { R = 0, G = 255, B = 0 } },
            { Time = 2, Alpha = 255, Scale = 10, Color = { R = 0, G = 255, B = 0 } },
            { Time = 3, Alpha = 0,   Scale = 12, Color = { R = 0, G = 255, B = 0 } },
        },
    },
    Properties = { ... },   -- read-only reference; never shipped
},

-- 669 = the sparks; tiny + short-lived, so LiveTime/StartScale/StartAlpha are bumped too
[669] = {
    Spt = ".\\Chef\\55LV_WEAPON\\55AXE\\669p.spt",
    Override = {
        StartColor = { R = 0, G = 255, B = 0 },
        LiveTime   = 2,
        StartScale = 3,
        StartAlpha = 255,
        Keys = {
            { Time = 2, Alpha = 0, Scale = 5, Color = { R = 0, G = 255, B = 0 } },
        },
    },
},
Recipe for a durable particle recolour: set StartColor and a Color on every Keys frame — writing Keys replaces the whole track. If the emitter is small or short-lived, also raise LiveTime / StartScale / StartAlpha so the change is actually visible. Then save the runtime file — it hot-reloads and re-pushes in about a second, and the particle updates on its next emit with no relog, no restart, no rebuild.
The Override block must sit next to Properties, not inside it. It is a sibling key of the same row. Putting StartColor inside Properties is the no-op trap described in READ FIRST.

The Override grammar

Every key is optional; supply only what you want to change. Colour and alpha values are 0–255.

KeyFormatMeaning
StartColor{ R, G, B } (0–255) — or { X, Y, Z }The particle’s base tint. Multiplies the sprite texture.
StartAlphanumber 0–255Starting opacity.
NumnumberHow many particles spawn per burst (density).
LiveTimenumberHow long each particle lives.
TimeSpeednumberPlayback rate of the emitter / animation.
StartScalenumberStarting size of each particle.
Gravity{ X, Y, Z }Downward / directional pull on particles.
StartPower{ X, Y, Z }Initial velocity of each particle.
AlphaTypenumberBlending mode selector (stock alpha_type).
ZFrontnumberDepth offset — pushes the particles in front of / behind the mesh.
Keys{ { Time=, Alpha=, Color={R,G,B}, Scale= }, ... }Keyframe tracks over a particle’s life. Each key must carry Time; Alpha, Color, Scale are optional. Maximum 12 keys.
Override = {
    StartColor = { R = 0, G = 255, B = 0 },
    StartAlpha = 255,
    Num        = 6,
    LiveTime   = 3,
    StartScale = 1.2,
    Gravity    = { X = 0, Y = -20, Z = 0 },
    Keys = {
        { Time = 0, Alpha = 255, Color = { R = 0, G = 255, B = 0 }, Scale = 1.4 },
        { Time = 3, Alpha = 0,   Color = { R = 0, G = 80,  B = 0 }, Scale = 0.2 },
    },
},

SkinFX: retarget an effect / field edits

Where SptIndex tunes the particles, SkinFX.lua tunes the effect files (the .EFF ribbons, auras and glows) that every client already loaded at login. It has three lists, all off until you set SkinFX.Enable = true.

Retargets — point one glow at a different stock effect

Redirects an effect slot (by its EffectID in EffectFileList.txt, 1…2099) to another .EFF that every client already has on disk. This is how you swap a whole look without touching binaries.

Retargets = {
    { EffectID = 2, EffPath = ".\\Chef\\Eff\\Bb\\KNIFE\\KN_LV30.EFF", DryRun = false },
},

Fields — edit one property of an effect

Addresses an effect by its exact (uppercase) EffPath and one Prop name from the registry. Record = -1 hits every record in the file. The value goes in the field matching the property’s kind: Value (float), Color (0xAARRGGBB), Vals (four floats), or Text (a short string).

Fields = {
    -- tint a weapon glow + crank its scroll speed
    { EffPath = ".\\CHEF\\EFF\\BB\\SWORD\\SW_LV30.EFF", Record = -1, Prop = "TextureFactor",     Color = 0x80FF2020 },
    { EffPath = ".\\CHEF\\EFF\\BB\\SWORD\\SW_LV30.EFF", Record = -1, Prop = "EffectScrollSpeed",  Value = 0.5 },
    -- move an attached particle outward on Z
    { EffPath = ".\\CHEF\\EFF\\BB\\SWORD\\SW_LV30.EFF", Record = -1, Prop = "Particle0Z",         Value = 0.35 },
},

Some useful registry Prop names

PropKindOn screen
TextureFactorcolorGlow tint + intensity (the alpha byte is overall strength).
EffectScrollSpeedfloatUV texture scroll speed — how fast the effect animates.
AlphaSpeedfloatFade / transparency cycling speed.
Particle0ID / 1 / 2dwordWhich particle index an effect attaches.
Particle0X/Y/ZfloatThe attachment point of that particle on the mesh.
Texture1 / Texture2 / TexturePathstringRe-point the texture file / folder an effect uses (≤ 20 chars).
DiffuseColor / AmbientColor / EmissiveColor / SpecularColorfloat4The character material colours (RGBA floats 0..1).
AlphaDensityfloatWhole-object opacity (0..1).
ParticlePoolScaleX/Y/Z, EntityPoolScale/Rot*float / dwordEdit a shared particle / entity pool slot (addressed by Index) for every user of it at once.

The full, authoritative list of editable properties — with each one’s struct, kind and on-screen meaning — is the Props table in SkinPropRegistry.lua. Adding a new editable is a single new row there; nothing is hard-coded in the server or client.

Finding your item’s indices & the authoring loop

  1. Get the item code. Note the exact code of the item you can see in-game (e.g. a weapon iwxzl55).
  2. Look up its particles. Open the matching slot file (WeaponSkin.lua, CloakSkin.lua…) and find that code’s record. Its Effect.Glow entries give the .EFF paths (for SkinFX) and its Attached.Particle entries give the particle indices (for SptIndex.Override). Write them all down — expect a handful per item.
  3. Add an Override to each index. In the runtime SptIndex.lua, add a sibling Override = { StartColor = { R=.., G=.., B=.. } } to every one of those indices.
  4. Save, look, adjust. The live push reaches your client in ~1–2 s. If the sparkles moved, iterate; if nothing changed, you likely still edited Properties, hit the source file not the runtime one, or the visible emitter is a solid .EFF (a SkinFX job).
  5. Commit. Copy the runtime file back to the _server\...\ini\SkinMod\ source folder.
Debugging an edit that “did nothing”Open .Server\Zoneserver\RF_Bin\ModulesLog\ and check the WeaponSkin.lua.log / _ALL PROBLEMS file. A successful reload logs a line like particle prop writes N. If N is 0, the server read no Override blocks (you edited Properties, or edited the wrong file). Malformed or unknown-index rows are logged and skipped — they never crash the server or client.

Rules & limits

  • Override, don’t edit, Properties. Properties and Parsed are read-only dumps; only Override (and SkinFX rows) are shipped. This is by design — the on-disk .spt / .EFF / .r3e art is never modified.
  • Lua files only. No binary asset is written. A Retarget must name a stock effect file every client already has; brand-new art needs a client patch, not this feature.
  • Colours are 0–255 in a particle Override / StartColor; SkinFX colour props are 0xAARRGGBB; material float4 props are 0..1 floats.
  • Keys cap at 12 and every key needs a Time.
  • Shared indices are global. A particle / entity pool slot change affects every item that uses it, and all changes apply to every player (per-player appearance is deliberately not offered). The particle / entity pool size is fixed for the session.
  • Malformed rows are rejected, never crash. An unknown index or an out-of-allow-list offset is logged with a one-line warning and ignored; the client refuses to write it.
  • Current binaries required. Live push only reaches a Zone server exe plus a matching rebuilt RF_Online.bin that carry Skin-Mod support; older binaries read the config but show nothing.
