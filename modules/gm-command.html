GM Command Whitelist

Server-only Ships enabled Hot-reload

What it does — and why you would use it

The server has roughly 230 built-in GM commands — short words you type into normal chat with a % in front of them to do things like report your position (%repo), set your level (%lv 50), teleport to a player (%gotochar Name) or disconnect somebody (%kick Name). Out of the box they are reserved for accounts carrying a GM degree: an ordinary player who types one just gets >> ERROR (authority).

That is all-or-nothing. This module gives you the middle ground: name the players you trust, and only those players get the commands — without creating a GM account, without touching the database, and with no idea required. It is the handy way to let a handful of mature players run events, test content, or help moderate while you are away.

PartWhere it livesIts job
On/off switch.Server\Zoneserver\RF_Bin\Modules\GMCommand\GMCommand.iniOne key, [General] Enable. Required at boot — do not delete the file.
The list & the manual.Server\Zoneserver\RF_Bin\Modules\GMCommand\GMCommand.luaSits beside the ini and holds both tables: GMCommand (who is allowed) and CommandList (the 260-line command reference the in-game %help reads).

Every use is loggedA whitelisted player’s command is written to the same cheat log a real GM’s command is: .Server\Zoneserver\ZoneServerLog\ServiceLog\Cheat<day>.log, one line per command as [ CharacterName ] >> %lv 50. The module itself also reports its state into Module Logs — GM Command Whitelist.log tells you how many names and how many catalog entries it loaded.

How to activate it

  1. Open the Lua file. Edit .Server\Zoneserver\RF_Bin\Modules\GMCommand\GMCommand.lua in Notepad. It opens with a plain-English guide describing both tables.
  2. Put in real names. Replace the placeholder lines in the GMCommand = { ... } block with the exact character names (the name on the character, not the account). See The player whitelist.
  3. Check the switch. Unlike most modules, this one ships on (Enable=1), so the shipped placeholder list is already live. If you want nothing to happen until you name someone, leave the list with only commented-out lines and it behaves like stock.
  4. Save — that is it. No restart: a running Zone server notices the edit on the next game tick (about a second) and reloads both tables. The module log records the reload.
  5. Revoke at any time. Delete a line (or put -- in front of it) and save. That player loses command access immediately — but see the one caveat in Rules & limits.
Do not delete either fileGMCommand.ini and its sibling GMCommand.lua are both required when the Zone server starts — a missing file stops the server from booting. To turn the feature off, set Enable=0 in the ini instead; the command catalog stays browsable for real GMs even while the whitelist is off.

The player whitelist

The first table in the file is the whole access list — one line per player:

GMCommand = {
  { PlayerName = "test" },
  { PlayerName = "PlayerName2" },
  { PlayerName = "PlayerName3" },
}
  • PlayerName — the character’s exact name, in quotes. Matching ignores capital cases, so test also matches Test.
  • Add a line to grant, delete a line (or comment it with --) to revoke. Saving applies it live.
  • There is no limit to the number of names; the shipped file carries 10 placeholders for you to overwrite.

Once listed, that player may type any command the server knows in ordinary chat with the % prefix. The whitelist only ever adds access: real GM accounts keep their normal degree-based rules untouched, and an unlisted player typing % still gets the plain >> ERROR (authority) reply that only they can see.

Where to find a nameCharacter names are exactly as the player appears above their head / in your friend list. Ask the player to type %repo once added: it is harmless, and it answers with their map and coordinates, confirming the name matched.

The %help command list

Nobody can memorise 230 commands, so the same Lua file carries a second table, CommandList, that documents all 260 accepted command names (every alias is its own row, so the list matches exactly what the server takes). Authorized users — whitelisted players and real GMs — can browse it inside the game:

You typeYou get
%helpThe count of commands, then every command name listed in compact pages of private chat (only you see them).
%help lootEvery command whose name starts with loot, one line each: %loba - Open the loot bag. — syntax plus description.
%help kickThe same detail for a single command when you already know most of its name.

Each catalog row is three plain fields, and you can edit any description, add your own notes, or drop lines you never want advertised — it hot-reloads exactly like the whitelist:

{ Command = "kick", Syntax = "<name>", Description = "Disconnect a player." },
  • Command — what the player types after the %.
  • Syntax — the extra words the command needs; angle brackets like <name> mean a value you must supply, and an empty "" means the command takes none.
  • Description — a short English explanation of what it does.
The catalog grants nothingCommandList is reference text only. Access comes from the GMCommand table alone — adding a command row does not unlock it for anyone, and deleting a row does not stop a real GM from using it. It is also read while Enable = 0, so GMs keep the in-game manual even when the whitelist is switched off.

Rules & limits

  • All or nothing, on purpose. A listed player gets every command, including the destructive ones — kick, ban-style punishment, wiping an inventory, spawning items, changing level. There is no per-command gate in this version, so only list people you would happily hand a GM account to.
  • Revoke means delete the line. Removing a name stops their next command instantly. The one thing to remember: a whitelisted player can type %change degree, which raises their GM degree for the rest of that session so they stay powerful until they log out. If you ever cut someone off in a hurry, also kick them (%kick Name from another authorized account, or via the GameCP) so the session — and any raised degree — dies. The database is never rewritten, so they come back an ordinary player.
  • It is chat, not a console. Commands are typed in the normal chat box with % in front, and argument parsing is exactly the stock GM parser’s: the first word is the command, the next up to five words are its arguments, so values containing spaces are not possible.
  • Some names overlap chat shortcuts. # in front of a line is the GM-whisper shortcut and ! is the operator line, so the class-change command has to be written %# rather than plain #. The catalog entry for it says so.
  • Nothing shows on the client. This is a server-only module: it takes no slot in the client feature-state packet and adds no button or window. Players only ever notice that their % lines work, and %help.
  • Old clients are still gated locally. The permission is server-side, but a player running an outdated RF_Online.bin (one from before this module) will find their % line never leaves the chat box. Make sure everyone using the feature has the current client build.

With Enable = 0 the whitelist is ignored completely and authority reverts to the stock GM-degree rules; real GM accounts keep working exactly as before, and %help remains available to them.
